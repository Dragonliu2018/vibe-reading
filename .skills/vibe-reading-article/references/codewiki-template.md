# CodeWiki 文档模板

概览（`00-overview.md`）和模块文件（`01-{module}.md`...）的章节结构模板。流水线执行见 `codewiki-workflow.md`，本文件只定义产出结构。

---

## 通用 Frontmatter

所有文件共享同一 source 和 category：

```yaml
---
source:
  type: "源码解读"
  project: "{project-name}"
  url: "{repo-url}"
title: "Overview"                        # 概览固定为 "Overview"；模块文件改为 "{模块名}"——**用中文**（如"执行引擎"、"注意力后端"），英文专有名词保留原文（如"PD 分离"），不加项目前缀和"详解"后缀（由 source 自动生成）
date: "YYYY-MM-DDTHH:MM:SS+08:00"      # 取博客编写时的当前时间（TZ=Asia/Shanghai date '+%Y-%m-%dT%H:%M:%S+08:00'，勿手填近似）；ISO 8601 带时区（北京时间）；同日多篇按完整值排序，展示截前 10 字符
category: [Domain, Project, CodeWiki, "{version}"]
tags: ["项目名", "语言", "核心标签"]
description: "一句话描述"
readingTime: "N min"
aiModel: "Claude Opus 5"
reviewed: false
---
```

> `source.type = "源码解读"`，前缀自动生成 `[project 源码解读]`（如 `[mycli 源码解读]`）。所有文件共享同一 source 和 category。

> `category` 末级用 `CodeWiki` + 版本号（引号包裹，如 `"1.2.0"`）。所有文件共享同一 category。徽章显示 `CodeWiki`（而非版本号），与 `Docs` 同理。版本号取 Step 0 的 tag（如 `v1.2.0` → `"1.2.0"`，去掉 `v` 前缀）。
>
> **无 tag 代码库**：版本号用 `<主分支名>-<YYYY-MM>`（`<主分支名>` = 仓库默认分支如 `main`/`master`/`develop`/`trunk`，**不一定是 `main`**；完整年份，如 `"main-2025-12"`/`"master-2025-12"`，不要 `main-2512`），`YYYY-MM` 取解读基线 commit 的提交年月。导言版本行追加 **解读基线** commit（短 hash + 日期 + 指向该 commit 的链接），锁定确切基线。完整格式与取主分支名/commit 信息的命令见 `codewiki-workflow.md` Step 0。
>
> **含空格的分类元素**：frontmatter `category:` 数组保留原样（含空格、用引号包裹，用于显示）；文件目录路径和文章内链接路径把空格替换为 `-`。规则见 `markdown-style.md`「文件命名」。

## 概览文件（`00-overview.md`）模板

> **章节不是刚性清单**——下面标注【必选】的章始终保留；标注【可选】的按代码库特点取舍，没有对应内容就省略，**不要写空壳章节**（"本项目无 X"比没有该章更差）。取舍依据见每章的"保留条件"。

```markdown
> **版本** v1.0.0 · **协议** MIT · **语言** Python ≥ 3.10 · **代码量** ~18,000 行 · **仓库** [GitHub](repo-url)

---

## 总览                                              【必选】
这一章的目标是让读者**还没看代码就知道项目在干什么**。如果代码库（尤其 README）含有下面相关内容，验证正确后直接参考借鉴。

### 项目简介                                         【必选】
...（Step 0 元信息。覆盖以下要点，不要逐条罗列、融成段落或表格：
- 项目是什么
- 解决什么业务/技术问题
- 核心价值是什么
- 核心使用场景
- **项目当前边界**：负责什么、不负责什么——1-2 句，避免读者误解项目范围）

### 功能矩阵                                         【必选】
...（| 特性 | 实现文件 | 说明 |。展示项目的核心功能与对应实现文件的映射）

### 技术栈                                           【必选】
...（使用的编程语言、框架、核心依赖库。用表格展示，附用途列：| 依赖 | 类型（核心/可选） | 用途 |）

### 版本历史                                         【可选】
...（主要版本演进和关键里程碑。解读特定 tag 时，简述该版本在演进中的位置即可，不写完整 changelog）
保留条件：项目有明确的版本演进脉络（如重大架构变更、重写）。无明显里程碑则省略。

### 顶层上下文图                                     【可选】
...（C4 Level 1：系统与外部角色/系统的关系。展示本项目与用户、外部服务、上下游系统的边界）
保留条件：系统有外部交互方（用户/第三方服务/上下游系统）。纯本地工具（如 CLI、库）无外部交互则省略。

## 快速上手                                          【必选】
...（**不要写成完整安装手册**，而是告诉代码阅读者："怎样最快看到这个项目真正跑起来？"如果代码库（尤其 README）含有相关内容，验证正确后直接参考借鉴。只给**外部操作 + 结果验证**：
- 环境、构建、运行的最简步骤（一条命令或几行代码，不展开可选配置）
- 一个端到端的示例验证（命令 + 预期输出，证明"跑起来了"）

**注意**：只写"用户视角的操作和结果"，**不展开内部调用链**（main 走了哪些步骤、连接怎么建立等留给「运行时行为 > 启动流程」）。两章分工：快速上手回答"怎么让项目跑起来"，启动流程回答"跑起来时内部发生了什么"。）
> 纯库/SDK 无"跑起来"概念时，改为"最小调用示例"——一段最简代码调用 + 预期输出。

## 架构设计解析                                       【必选】
如果代码库（尤其 README）含有架构图等信息，验证正确后直接使用。

### 系统架构                                         【必选】
...（展示系统的整体架构设计。**应该先讲架构思想**——为什么这样设计，解决什么问题。然后引用 Step 4.1 分层架构图 SVG，配一段文字，条理清晰地介绍系统架构——讲清楚分了几层、各层职责和依赖方向、层间如何协作、这样分层解决了什么问题。**不要机械复述 SVG 里的层名**，而是有逻辑主线地组织文字，让读者理解"系统整体怎么设计的、为什么"。图里只放层名和模块名，详细说明放在文字里。再把代码目录映射进去：

| 架构层  | 包含目录          | 层职责（为什么这层存在）              |
| ---- | ------------- | ------------------------- |
| 接口层  | `api/`        | 隔离外部协议，保护核心不受接口变化影响        |
| 应用层  | `service/`    | 编排用例流程，协调领域对象协作            |
| 核心层  | `core/`       | 承载业务规则，不依赖任何外部实现           |
| 数据层  | `repository/` | 封装持久化细节，对上提供领域语义的接口       |
| 基础设施 | `infra/`      | 适配外部资源（DB/MQ/第三方），可替换        |

**注意**：映射表的"层职责"写架构角色（这层为什么存在、解决什么问题），**不要写目录内容**（"接收外部请求""数据访问"等具体描述留给「代码目录」章）。两章分工：分层设计回答"这个目录属于哪层、为什么"，代码目录回答"这个目录里有什么文件"。）

### 设计模式                                         【可选】
...（采用的关键设计模式和架构原则。Step 4.4 设计模式汇总表格）
保留条件：识别到 3+ 个设计模式。只有 1-2 个则并入分层设计，不单独成节。

### 核心概念                                         【可选】
...（回答"项目里最重要的'东西'是什么"。核心抽象定义了扩展点的契约，具体如何扩展见「典型修改场景」。Step 4.5 汇总。）

#### 核心对象
...（领域模型/核心数据结构，如 Task、Pipeline、SQLResult。整理为对象表（| 核心对象 | 含义 | 生命周期 | 主要关系 |）+ 对象关系图 ASCII。回答"项目里有什么"。）

#### 核心抽象
...（基础接口/抽象类及其关系，如 `TaskHandler` 接口、`BasePlugin` 抽象类、`Completer` 基类——扩展点的契约。用简表说明：| 接口/抽象类 | 定义位置 | 实现类 | 注册方式 |。回答"项目怎么被扩展"。）

保留条件：有明确的领域模型/核心数据结构，或有值得讲的核心接口/抽象类。纯工具库无领域模型且抽象简单则省略。

## 代码目录                                           【必选】
...（这一章才真正解释 repository tree。Step 1.1 目录树。例如：

```shell
project/
├── app/
│   ├── api/             # API入口
│   ├── service/         # 业务编排
│   ├── core/            # 核心逻辑
│   ├── repository/      # 数据访问
│   └── models/          # 数据模型
│
├── configs/             # 配置
├── scripts/             # 运维/辅助脚本
├── tests/               # 测试
└── main.py              # 程序入口
```

但**不要每个文件都解释**。只解释：
- 一级目录
- 关键二级目录
- 关键入口文件
- 特殊目录

详细文件级分析留给重点模块文档。`tests/` 目录只标"测试"不展开子目录——测试分层结构留给「测试体系」章。

**与模块地图的分工**：代码目录只讲文件系统结构（有哪些目录/文件、目录树长什么样），不展开模块职责和依赖关系——那是「模块地图」的事。如果一个模块≈一个目录，代码目录只标注"这个目录有什么文件"，模块地图负责回答"这个模块为什么独立、职责是什么、依赖谁"。）

## 模块地图                                          【必选】
...（**单层**：列全部模块表（| 模块 | 职责 | 核心入口 | 为什么独立 | 深入阅读 |），引用全局 `module-dependencies.svg`。模块数无上限，全部列出。某模块有深度解读附件时，在"深入阅读"列同时链接模块文件和附件。

引用 Step 4.2 `module-dependencies.svg`（模块依赖关系图，展示横向组件间的 import/调用关系），配一段文字描述模块间的依赖方向和交互方式。然后放模块表：| 模块 | 职责 | 核心入口 | **为什么独立** | 深入阅读 |。"为什么独立"一句话说明该模块独立存在的理由，比解释 10 个类更有价值。不重复列目录路径——文件系统结构见「代码目录」。

**与运行时行为的交叉引用**：模块地图讲静态职责和依赖，运行时行为的核心运行流程讲动态业务链路（跨模块调用）。两者都涉及模块间关系但视角不同。模块表可加一列"参与的业务链路"（引用核心运行流程中的链路名，如"请求处理主链路"），让读者从静态模块表跳到动态调用链；或加一句交叉引用提示"模块间的动态调用顺序见运行时行为 > 核心运行流程"。）

## 运行时行为                                         【必选】
这一章回答"程序到底是怎么跑起来的"——从进程启动到业务链路再到数据流变化，完整展现运行时行为。

### 启动流程                                         【必选】
...（Step 1.3 入口调用链。一次性启动：main → 初始化 → 连接 → 模式分发。用 ASCII 调用链展示，标注每步的文件路径和职责。

在"初始化"环节展开讲清对象装配，回答"这个对象到底是谁 new 出来的？"：
- 配置来自哪里（文件/环境变量/命令行），覆盖优先级是什么
- 对象实例化顺序（谁先创建、谁依赖谁）
- 依赖注入方式（DI 容器/手动 new/工厂方法）
- 单例在哪里创建、组件如何注册（如 Plugin 注册、Service 如何拿到 Repository）

这样启动流程同时覆盖"调用顺序"和"对象怎么组装"，不再单设配置与初始化子节。
> 库/SDK 没有"启动"概念时，改为"初始化流程"——讲模块加载、配置读取、资源准备、对象装配。）

### 核心运行流程                                     【必选】
...（选 3+ 条最重要的业务链路。**先写一段简洁的介绍段落**，总结后续链路覆盖了哪些运行模式和核心场景，让读者在看每条链路前先有整体认知。然后每条链路用 `####` 子章节，给出**业务流程 + SVG/文字描述**。这是整个概览最重要的一节——很多代码解读文档最大的问题就是讲了一堆类，却没回答"程序到底怎么跑起来的"。概览只讲主链路，更多链路的细节留给模块文档。

**注意**：每条链路用 **SVG 图 + 文字描述**，不要同时放 SVG 和 ASCII 调用链——两者重复。SVG 负责一眼看懂流向，文字解读负责关键方法名、数据结构变化、设计决策。ASCII 调用链的细节级别留给模块文档。例如：

#### {分类标签}：{链路名称 1}

业务流程：用户提交任务 → 参数校验 → 创建任务 → 执行 → 保存结果 → 返回

![数据流 SVG](/vibe-reading/images/articles/{slug}/data-flow.svg)

文字描述：从入口方法出发，概括每步调用的方法名、数据结构变化（如 RawRequest → RequestDTO → Task → Result）、关键设计决策（如降级、流式、并发）。一段话讲清整条链路，不复述 SVG 图里已有的节点和箭头。

#### {分类标签}：{链路名称 2}
...（同上，另一条业务链路。）

### 状态流                                         【可选】
...（如果项目存在状态机或对象有明确的生命周期状态，单列状态流转图。**用 SVG 图**（与全文架构图/调用链路/数据流风格一致），不用 ASCII——状态机的分支与回环用 SVG 箭头表达比 `├─└─` 直观。Step 4 生成 `state-flow.svg` 存入 `public/images/articles/{slug}/`。SVG 后紧跟文字，指出相关代码：状态枚举定义在哪、状态转换方法是什么、谁触发转换。

**注意**：状态流只做**全状态机汇总**——画出完整的状态图（所有状态 + 所有转换路径），不复述核心运行流程中单条链路涉及的状态。核心运行流程讲"这条链路里状态怎么走"，状态流讲"所有状态的全貌和转换规则"。两节分工：单链路片段 vs 全状态机。多个独立状态机（如连接状态 + 刷新状态）可合并到一张 SVG 分区展示，或各出一张小 SVG。）
保留条件：项目有明确的状态机或对象生命周期状态（如任务状态机、连接状态、会话状态）。无状态流转则省略。

## 典型修改场景                                      【可选】
...（Step 4.6 汇总的 3 个代表性场景，每个用 `####` 子章节，列出需修改的文件和关键函数。让读者知道改一个需求要动哪些地方。扩展点的契约定义见「架构设计解析 > 核心概念」的核心抽象。每个场景末尾标注对应测试路径（如"对应测试：tests/unit/test_xxx.py"），与测试体系交叉引用——改代码时顺手看测试。）

#### 场景 1：{场景名}
...（需修改的文件和关键函数列表。）

#### 场景 2：{场景名}
...（同上。）

#### 场景 3：{场景名}
...（同上。）

保留条件：有可枚举的扩展点（插件系统、命令注册、Handler 注册等）。纯算法库无扩展点则省略。

## 测试体系                                          【可选】
...（讲清楚测试目录结构和测试分层。例如：

```
tests/
├── unit/           # 单元测试
├── integration/    # 集成测试
├── e2e/            # 端到端测试
└── fixtures/       # 测试夹具
```

以及测试与代码的对应关系：

| 代码层 | 测试类型 |
|--------|----------|
| Domain/Core | Unit Test |
| Repository | Integration Test |
| API | E2E Test |

还可以指出：如果想理解某个类，优先阅读它对应的测试。很多优秀项目里，测试实际上是非常好的"可执行文档"。修改某层代码时，参照上表找到对应测试类型优先阅读——与典型修改场景的测试路径标注互相呼应。）
保留条件：项目有成体系的测试目录（unit/integration/e2e 分层）。只有零散测试或无测试则省略。

## 阅读源码推荐路线                                  【必选】
...（替读者规划 3-4 遍阅读路径，不要让读者自己从 src/ 猜从哪里开始。**必须给文件级路径，不是章节级路径**——独特价值是告诉读者"打开哪个文件先读"，不是"看哪个章节"。路径粒度到文件，重要时可细化到类或方法。例如：

- 第一遍：理解主流程
  `main.py` → `cli_runner.py` 的 `run_from_cli_args()` → `client.py` 的 `MyCli` → `sqlexecute.py` 的 `SQLExecute.run()`
- 第二遍：理解核心数据结构
  `sqlresult.py` 的 `SQLResult` → `sqlexecute.py` 的 `ServerInfo` / `ServerSpecies`
- 第三遍：理解扩展机制
  `special/main.py` 的 `@special_command` + `execute()` → `completion_engine.py` 的 `SuggestRule` + `suggest_type()`
- 第四遍：选择重点子模块深入阅读（模块文档；若有深度解读附件，从模块文件的对应章节链接进附件）

每遍标注具体文件路径（重要时含类/方法）和该处读什么，而非"看运行时行为章""看核心概念章"——那是目录重排，对读者无增量价值。）
> 小项目路径可少于 4 遍，但至少给出"从哪个文件/方法开始读"的指引。

## 附录                                              【可选】
...（按需收录：
- **术语表**：专业术语解释（项目特有的概念、缩写、领域名词）
- **参考资料**：相关文档、论文、博客链接（官方文档、设计文档、引用的论文等）
- **工具推荐**：开发、调试、分析工具介绍（如 profiler、debugger、可视化工具））
保留条件：有需要解释的术语或有价值的参考资料。无则省略。

## 深度解读附件（`{NN}-{module}-{topic}.md`）模板

> 当某模块内有特别复杂或重要的设计/算法/实现值得单独展开时，为它写一篇深度解读附件。附件与模块文件平级（同目录、独立 frontmatter），从模块文件的合适位置（如「核心实现」章节）链接过来。附件不是新层级，不列在概览模块地图里——它是模块的"深入阅读"。

```markdown
> [← 返回{模块名}](/vibe-reading/articles/{category_path}/{NN}-{module})

## 模块架构                                          【必选】

## 调用链路                                          【必选】

## 通用规范

**子文档链接**：概览的"模块地图"表格链接到各模块文档，链接路径为 `/vibe-reading/articles/{category_path}/{NN-module}`（不含 `.md` 扩展名）。深度解读附件从对应模块文件的合适位置链接（`/vibe-reading/articles/{category_path}/{NN-module}-{topic}`），不列在概览模块地图——它是模块的深入阅读，不是顶层导航项。

**写作规范**：
- 正文中文，专有名词（框架名、函数名、路径）保留英文原文
- 引用源码中真实的路径和函数名，不编造 API
- 代码块必须标注语言和 `title="文件路径"`
- 每个 `##` 节有实质内容（代码 / 表格 / 图片），不写空泛段落
- SVG 图片用 `![alt](/vibe-reading/images/articles/{slug}/{filename}.svg)` 引用，alt 即图注
- 不含 `layout:` 行（由路由统一处理）
- **README 优先复用**：如果代码库（尤其 README）已包含项目简介、架构图、功能列表等信息，验证正确后直接引用/复用，不重复造轮子

**反偷懒规则**（承自 Step 3，撰写时同样适用）：
1. 引用具体函数名和文件路径（`函数名 in 路径`），不许"有一个函数…"、"某处会…"
2. 解释设计决策的 why，不只描述代码做什么
3. 不确定时明确标注"待核实"，不要用模糊措辞掩盖
