## 模块定位

`src/pl/`（~13 万行）+ `src/objit/`（1.13 万行）+ `src/sql/ob_spi.cpp` 实现 Oracle 兼容的存储过程/函数/触发器/匿名块。**核心事实先纠正：PL 引擎是 LLVM JIT 直接生成本机机器码，不是"解释执行自定义 IR"**——objit 是"Object JIT"，封装 LLVM ORC JIT，"IR" 就是 LLVM IR，不存在自定义 IR 类。为什么 JIT：存储过程是长尾重计算逻辑（循环、递归、集合操作），解释器每语句一次 dispatch 在百万次循环下不可接受；JIT 后控制流零开销，只有数据操作回落 C++。SPI 类名为 `ObSPIService`（纯静态方法集合，`ob_spi.h:328`）。

`ObPLFunction`（编译产物）的核心成员是 `ObFuncPtr action_`——**JIT 生成的本机函数指针**；`ObPLExecCtx` 是 JIT 代码与 C++ 引擎之间的桥，字段布局用 `IDX_PLEXECCTX_*` 索引常量 + offsetof 静态断言固定（codegen 生成的每条 GEP 寻址指令都依赖它，改字段顺序即炸）。

## 调用链路

### CREATE PROCEDURE 编译（首次 CALL 触发）

```
ObPL::execute → get_pl_function（lib cache miss）
└─ ObPL::generate_pl_function                ob_pl.cpp:3466
   └─ ObPLCompiler::compile                  ob_pl_compile.cpp:423
      ├─ Step1 init_function（参数→ObPLDataType，登记依赖对象）
      ├─ Step2 ObPLParser::parse_routine_body（pl/parser/，独立 bison）
      ├─ Step3 ObPLResolver::resolve_root → ObPLFunctionAST（符号表+34 种语句）
      ├─ Step4 ObPLCodeGenerator::generate   ob_pl_code_generator.cpp:9453
      │   ├─ read_dll_from_disk              :370（磁盘 DLL 命中则免 JIT）
      │   ├─ generate_normal :9514
      │   │    └─ ObPLCodeGenerateVisitor 逐语句发射 LLVM IR
      │   │       → helper_.compile_module(PLSQL_OPTIMIZE_LEVEL)
      │   │       → get_function_address → func.set_action(addr)  本机函数指针
      │   └─ 或 generate_simple :9479 → set_action(&ObPL::simple_execute)
      └─ Step5 依赖登记（OB_ALL_TENANT_DEPENDENCY 表）
```

并发去重：`ObPL` 持一对 `ObBucketLock`——第一把按 routine_id 去重（多 session 同名 routine 只 JIT 一次），第二把按 `_ob_pl_compile_max_concurrency` 限并发。

### CALL 执行

```
ObCallProcedureExecutor::execute               sql/engine/cmd/ob_routine_executor.cpp:92
└─ ctx.get_pl_engine()->execute(...)           :253（ExecCtxBak 备份 SQL 帧）
   └─ ObPLExecState::init(params) → execute()  ob_pl.cpp:5436
```

## 核心实现

### SPI 完整借道 SQL 主链路

PL 内 SQL 与普通 SQL 有一致的优化/plan cache/重试/锁/事务语义——绕过 = 语义分裂。SPI 层只做三件事：参数求值与绑定、INTO 回写、session 状态隔离（`ObSPIExecEnvGuard`/nested session）。**SPI 重试的特别约束**：`ObSPIRetryCtrlGuard`（`ob_spi.cpp`）调 `test_and_save_retry_state` 时硬编码 `force_local_retry=true`（注释："in SPI, we can only do local retry"）——PL 调用帧在栈上无法回退重放，失败只能本地重试当前语句；重试前 `reset_member_for_retry` 清理 result set 状态并重新获取 schema guard。编译期就 `spi_prepare` 把静态 SQL 预解析成 `ps_sql_`（参数化 SQL，`ObPLSqlInfo::generate`，`ob_pl.cpp:5098`）——执行期免 parse 直接进 plan cache 匹配。PL 变量作用域通过 `PLPrepareCtx::secondary_ns_`（`ObPLBlockNS*`）注入 SQL resolve——SQL 里的 `:var`/裸变量能命中 PL 符号。PL 表达式也不是自造的：resolver 生成 `ObRawExpr` 存为 `ObSqlExpression`，执行期 `spi_calc_expr` 求值——**复用 SQL 表达式引擎**。

### "全 SQL 语句体"免 JIT 快路径

`ast.get_is_all_sql_stmt() && obj_access_exprs().empty()` 时 `generate_simple` 把 `action_` 设为静态 `ObPL::simple_execute`（`ob_pl.cpp:5137`）——顺序执行 `sql_infos_` 里的每条 SPI 调用。很多 routine 只是几条 SQL 的顺序包装（ETL/运维脚本），JIT 的编译耗时（毫秒级）+ 内存 + ORC runtime 开销不划算。

### 编译产物磁盘持久化（DLL 缓存）

`read_dll_from_disk` + `ObRoutinePersistentInfo` + `ObORCObjectCache`：JIT 编译比解析慢 1-2 个数量级，observer 重启后若所有 routine 重 JIT 会启动风暴——把 object file 存内部表，重启直接加载。由 `_enable_persistent_compiled_routine` 控制。

### 系统包自举

三层：① spec/body 以 `.sql` 存放于 `src/share/inner_table/sys_package/`（114 个文件），构建期 `syspack_codegen.py` 生成注册表；② 启动时 `ObPLPackageManager::load_all_sys_package` 用 **PL 编译器自身**编译——系统包与用户包走完全相同的编译/缓存路径（自举，行为一致）；③ 性能敏感子程序经 `INTERFACE_DEF` 表（`ob_pl_interface_pragma.h:100-998`）落到 C++，body SQL 中 `PRAGMA INTERFACE` 声明。

### 诊断与异常

DWARF 全链路：`ObLLVMDIHelper`（生成）→ GDB `__jit_debug_descriptor`（ORC JIT 注册，可逐行调试 PL）→ `ObDWARFHelper`（执行期地址→行号）。PL 异常用 C++ 异常 + LLVM personality func，`inner_call` 场景捕获后 `_Unwind_RaiseException` 原样重抛跨帧传播。

## 设计模式

| 模式 | 位置 | 为什么用 |
| --- | --- | --- |
| Visitor | `ObPLStmtVisitor`（`ob_pl_stmt.h:3592`，34 个纯虚 visit）+ `ObPLCodeGenerateVisitor` | AST 结构与 IR 生成解耦；接口演进不静默 |
| 帧栈 | `ObPLContext::get_exec_stack()` + `ExecCtxBak` 逐属性备份 | PL 帧与 SQL 帧互不污染（pl 栈↔sql 栈交替） |
| 签名适配模板 | `interface_checker<T,func>`（`ob_pl_interface_pragma.cpp:20-56`） | 4 种 C++ 签名统一适配为 PL 调用约定 |
| 兼容层 | `co_var.h` 的 RLOCAL→thread_local | 协程移除后老代码零改动 |
| Guard 全家桶 | `ObPLCompilerEnvGuard/ObSPIRetryCtrlGuard/LinkPLStackGuard...` | PL/SQL 交互的每个状态都要备份恢复 |

## 模块间交互

依赖 sql/parser（PL 内 SQL 文本借主 parser 解析）与 resolver 的表达式工厂；SPI 借道 `GCTX.sql_engine_`；被 `ObCallProcedureExecutor`/`ObAnonymousBlockExecutor`（sql/engine/cmd）、`TriggerHandle`（sql/engine/dml）、GET DIAGNOSTICS executor 调用。objit 与主库解耦：`pl/` 只 include objit 的 3 个头，LLVM 头文件隔离在 objit 内部（独立 deps/build），避免 LLVM 符号污染主二进制。外部例程 `pl/external_routine/` 支持 CPython/JNI 的 PL 调 Python/Java UDF。

## 扩展方式

- **新增系统包 DBMS_FOO**：`sys_package/dbms_foo.sql` + `dbms_foo_body.sql`（构建期自动注册，零 C++）；需 C++ 原生子程序时 `pl/sys_package/ob_dbms_foo.cpp` 实现 + `ob_pl_interface_pragma.h` 加 `INTERFACE_DEF(INTERFACE_DBMS_FOO_XXX, "XXX", (ObDBMSFoo::xxx))` + body 中 `PRAGMA INTERFACE`
- **新增一种 PL 语句**：`pl/parser/` bison 加节点 → `ob_pl_stmt.h` 加 Stmt + **`ObPLStmtVisitor` 加一个纯虚 visit（强制所有 Visitor 同步修改——接口演进不静默）** → resolver 加分支 → code generator 加 `visit(const ObPLXXXStmt&)` 发射 IR
- **新增复合类型**：`ob_pl_user_type.h`（ObRecordType/ObCollectionType/ObPLNestedTable/ObPLAssocArray/ObPLVArray 继承树）+ `generate_user_type`（`ob_pl_code_generator.cpp:3849`）生成 LLVM 结构体类型
