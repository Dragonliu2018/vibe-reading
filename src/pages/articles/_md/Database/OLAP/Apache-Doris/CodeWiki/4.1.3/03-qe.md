## 模块定位

查询协调模块（`fe/fe-core/.../qe/` + `mysql/`）负责从 MySQL 协议接入到 Fragment 调度结果回传的全过程。它管理连接会话、分发 SQL 到 Nereids 优化器、把物理计划序列化分发到多个 BE、流式拉取结果返回客户端。独立成文是因为协议接入与分布式调度是独立于优化（Nereids）和执行（BE Pipeline）的关注点——它回答"计划怎么发到 BE、结果怎么收回来"。

## 模块架构

模块分四层：**协议层**（`MysqlServer` 基于 Xnio NIO 监听 9030、`MysqlProto` 握手认证、`AcceptListener`/`ReadListener` 异步事件分发）、**会话层**（`ConnectContext` ThreadLocal 上下文、`ConnectScheduler` 连接池、`ConnectProcessor` 抽象基类）、**执行入口层**（`StmtExecutor` 编排解析→计划→执行→结果）、**调度层**（`Coordinator` Legacy / `NereidsCoordinator` 新版委托 `CoordinatorContext`+`PipelineExecutionTask`）。

```
客户端 TCP
   │  MysqlServer (Xnio NIO, port 9030)
   ▼  AcceptListener → MysqlProto.negotiate (握手认证)
ConnectContext (ThreadLocal 会话) + ConnectScheduler (连接池)
   │  ReadListener → MysqlConnectProcessor.processOnce → dispatch
   ▼  COM_QUERY → ConnectProcessor.handleQuery → executeQuery
StmtExecutor.execute → executeByNereids
   ├─ NereidsPlanner.plan (生成物理计划)
   └─ NereidsCoordinator.exec
        ├─ processFragmentAssignmentAndParams (选 BE 副本)
        ├─ sendPipelineCtx (两阶段 gRPC 下发)
        └─ getNext (ResultReceiverConsumer 流式拉取)
   ▼  channel.sendOnePacket (MySQL 行包回客户端)
```

## 调用链路

一条 SELECT 从接入到返回：

```
MysqlServer.start (MysqlServer.java:70)
  → AcceptListener.handleEvent (AcceptListener.java:54)
    → new ConnectContext → connectScheduler.submit
    → MysqlProto.negotiate (MysqlProto.java:98)  // 握手+认证
    → new MysqlConnectProcessor → context.startAcceptQuery
  [客户端发 COM_QUERY]
  → ReadListener.handleEvent (ReadListener.java:43)
    → ctx.suspendAcceptQuery → worker.execute
    → MysqlConnectProcessor.processOnce (MysqlConnectProcessor.java:385)
      → fetchOnePacket → dispatch (MysqlConnectProcessor.java:243)
        → COM_QUERY → handleQuery
          → ConnectProcessor.handleQuery (ConnectProcessor.java:217)
            → NereidsParser.parseSQL + new StmtExecutor
            → executor.execute (StmtExecutor.java:500)
              → queryRetry → execute → executeByNereids (StmtExecutor.java:671)
                → new NereidsPlanner + planner.plan
                → handleQueryStmt → executeAndSendResult (StmtExecutor.java:1340)
                  → new NereidsCoordinator + coord.exec (Coordinator.java:692)
                    → execInternal → processFragmentAssignmentAndParams
                    → sendPipelineCtx (Coordinator.java:823)
                      → execRemoteFragmentsAsync (gRPC exec_plan_fragment)
                  → while(true) { batch=coord.getNext; channel.sendOnePacket(row) }
  → finalizeCommand (ConnectProcessor.java:630)  // EOF/OK 包
```

数据类型流转：TCP 字节 → `ByteBuffer`（MySQL 包）→ `String` SQL → `List<StatementBase>` → `LogicalPlanAdapter` → `NereidsPlanner` 产 `PlanFragment`/`ScanNode`/`DescriptorTable` → `TPipelineFragmentParams`（Thrift）→ gRPC bytes → BE；BE 回 `PFetchDataResult`（含 row_batch bytes）→ `RowBatch`（`TResultBatch`）→ `MysqlChannel.sendOnePacket`。

## 核心实现

### MySQL 协议异步接入

`MysqlServer`（`mysql/MysqlServer.java:41`）基于 Xnio NIO 框架，`start` 创建 `AcceptingChannel`，`AcceptListener.handleEvent` accept 新连接后 `new ConnectContext`、`connectScheduler.submit` 分配 connectionId、`MysqlProto.negotiate` 完成握手三步曲（发 HandshakePacket → 收 AuthPacket → 认证+设默认 catalog/db），最后 `new MysqlConnectProcessor` + `startAcceptQuery` 注册 `ReadListener`。`ReadListener.handleEvent`（`mysql/ReadListener.java:43`）检测可读后先 `suspendAcceptQuery`（避免重复唤醒）再提交 task 线程池异步执行 `processOnce`。

### 两阶段调度

`Coordinator.sendPipelineCtx`（`qe/Coordinator.java:823`）实现两阶段调度：`twoPhaseExecution = fragments.size() > 1`（`Coordinator.java:845`）。Phase 1 `execRemoteFragmentsAsync` 发 `PExecPlanFragment`，BE 接收后初始化 fragment 但不开始（`need_wait_execution_trigger = twoPhaseExecution`）；Phase 2 `exec_plan_fragment_start` 通知 BE 统一启动。**为什么两阶段**：多 fragment 查询中下游 fragment 的 ExchangeNode 必须先准备好接收 buffer，上游才能发数据，单阶段会导致丢包或阻塞。

### 副本选择与并行度

`Coordinator.computeScanRangeAssignment`（`Coordinator.java:2183`）按 fragment 特性选策略：**Colocate Join**（`computeScanRangeAssignmentByColocate`，相同 bucketSeq 的 tablet 分到同一 BE 保证 join 两端同机）、**Bucket Shuffle Join**（`computeScanRangeAssignmentByBucket`）、**通用调度**（`computeScanRangeAssignmentByScheduler` 轮询+最小负载）。`selectBackendsByRoundRobin`（`Coordinator.java:2336`）若 `enable_local_replica_selection` 优先本机 BE 副本，否则选 `assignedBytes` 最小的；`SimpleScheduler` 维护黑名单，BE 不可用时跳过。

并行度由 `parallelExecInstanceNum`（SessionVariable 默认 8，`Coordinator.java:1939`）控制 fragment 实例数，`computeFragmentHosts`（`Coordinator.java:1769`）为每个 BE 按 scan range 拆分实例。

### NereidsCoordinator 新版调度

`NereidsCoordinator`（`qe/NereidsCoordinator.java:79`）继承 `Coordinator`，把调度委托给 `CoordinatorContext`（不可变常量+可变状态）+ `PipelineExecutionTask`：`exec` → `enqueue`（WorkloadGroup 排队）→ `processTopSink` → `ThriftPlansBuilder.plansToThrift` → `PipelineExecutionTaskBuilder.build` → `executionTask.execute`。相比 Legacy `Coordinator` 的 `processFragmentAssignmentAndParams`+`sendPipelineCtx` 路径更模块化。

### 结果流式拉取

`ResultReceiverConsumer`（`qe/ResultReceiverConsumer.java`）管理多 `ResultReceiver`（每 BE 一个）轮询，`getNext` 从就绪的 receiver 拉 `RowBatch`。`ResultReceiver.createFuture`（`ResultReceiver.java:81`）预发下一个 `fetch_data` BRPC，处理当前 batch 时下一批已在途——混合拉取模型：BE 无数据时将 ctx 加入 `_waiting_rpc` 队列，pipeline 产出 Block 后异步回调 `GetResultBatchCtx.on_data` 序列化返回。`StmtExecutor.executeAndSendResult`（`StmtExecutor.java:1404`）`while(true)` 逐 batch `sendOnePacket`。

### SessionVariable 影响计划

`SessionVariable`（`qe/SessionVariable.java`）在多处影响执行：`parallelExecInstanceNum`（默认 8，fragment 实例并行度）、`enableShareHashTableForBroadcastJoin`（广播 join 共享 hash table）、`maxMsgSizeOfResultReceiver`（结果包大小）、`queryTimeoutS`（超时）、`bypassWorkloadGroup`（跳过排队）。通过 `toThrift` 序列化传给 BE，BE 在 `TQueryOptions` 读取。

## 设计模式

| 模式 | 位置 | 为什么用 |
| --- | --- | --- |
| NIO 事件分发 | `MysqlServer`+`AcceptListener`/`ReadListener` | 高并发连接，IO 线程检测+task 线程处理 |
| 两阶段调度 | `Coordinator.sendPipelineCtx` | 保证下游就绪后上游才发数据 |
| 委托 | `NereidsCoordinator`→`CoordinatorContext`+`PipelineExecutionTask` | 新版解耦，状态与逻辑分离 |
| ThreadLocal 上下文 | `ConnectContext` | 任意代码 `ConnectContext.get()` 取会话 |

## 模块间交互

调 `nereids`（`StmtExecutor.executeByNereids` 创建 `NereidsPlanner`）、`catalog`（`Env` 取元数据/认证/`SystemInfoService` 取 BE 列表，`Coordinator.prepare` 调 `Env.getCurrentSystemInfo().getBackendsByCurrentCluster`）、`rpc`（`BackendServiceProxy.execPlanFragmentsAsync` gRPC、`cancel` BRPC）、`load`（`NereidsCoordinator.setForInsert` 创建 `LoadProcessor`，非 ResultSink 走 load 路径）。地址转换 `toBrpcHost`/`toRpcHost`/`toArrowFlightHost` 适配不同 RPC。

## 扩展方式

新增 Session Variable：`SessionVariable.java` 加字段+`@VariableField` 注解（Tobster 框架自动处理 SET 命令）+`toThrift` 序列化；`Coordinator.initQueryOptions` 映射到 `TQueryOptions`；Thrift IDL 加字段；如影响 BE 执行，BE 侧 `pipeline_x_fragment_context` 读 `TQueryOptions`。

修改副本选择策略：改 `Coordinator.selectBackendsByRoundRobin`/`computeScanRangeAssignmentByScheduler`，或 `SimpleScheduler.getLocation`/`getHost` 黑名单逻辑；如新增选择维度（如优先 SSD）在 `system/Backend.java` 加属性。

新增 MySQL 命令：`mysql/MysqlCommand.java` 加枚举；`MysqlConnectProcessor.dispatch` switch 加分支；新增 `handleXxx`。
