## 模块定位

`qe/`（5.3 万行）是"从字节流到计划部署"的胶水层：MySQL 协议服务器、连接与会话管理、语句执行器 `StmtExecutor`、Fragment 调度器 Coordinator、查询队列与超时保护。它独立成篇是因为状态最杂——协议线程模型、会话 god object、调度三阶段、排队限流四件事都挤在这里，而每件都直接影响"查询到底怎么跑起来的"。

## 模块架构

协议层与调度层两块。协议层基于 **JBoss xnio**（不是 Netty）：`QeService.start()` → `mysql/MysqlServer.start()` 建 AcceptingChannel（IO 线程数 `Config.mysql_service_io_threads_num`，任务线程池 `starrocks-mysql-nio-pool`）。调度层已重构为接口 `qe/scheduler/Coordinator.java` + 实现 `qe/DefaultCoordinator.java`，配套 `qe/scheduler/` 子包（Coordinator v2 重构产物）。

## 调用链路

### 协议接入与命令分发

```text
AcceptListener.handleEvent()                        # accept
  → ConnectContext(connection) + MysqlProto.negotiate()   # SSL/能力协商
  → ConnectScheduler.registerConnection()           # qe_max_connection 全局连接数限制 (:132)
  → MysqlProto.authenticate()                       # 认证（早于任何 SQL）
  → context.startAcceptQuery(processor)             # 注册读监听
MySQLReadListener.handleEvent()                     # IO 线程只做读写
  → MysqlPackageDecoder.poll() 切 packet → 提交 worker 线程
  → ConnectProcessor.processOnce() (:996 switch)
      COM_QUERY        → handleQuery() (:680)
      COM_STMT_EXECUTE → handleExecute()
      COM_PING / ...   → handleXxx()
```

I/O 线程只做读写，命令处理在 worker 线程——`MySQLReadListener.killRunningQuery()` 注释解释了为何 kill 也要移交 worker：cancel 要抢 coordinator 锁，不能 park 稀缺的 xnio IO 线程。

### 查询调度三步（`DefaultCoordinator.startScheduling()`，:609）

1. **Pending**：`QueryQueueManager.maybeWait()`（`QueryQueueManager.java:57`，SingletonHolder 单例）构造 `LogicalSlot`（v2 按内存估算，`SlotEstimator`），`slotProvider.requireSlot()` 返回 Future 阻塞等 `SlotManager` 分配；排队期 `setPendingTimeSecond()` 顺延超时。
2. **Prepare**：`CoordinatorPreprocessor` 把每个 PlanFragment 实例化为多个 `FragmentInstance`（`TFragmentInstanceFactory`），经 `BackendSelector` 策略（Colocated/BucketAware/HDFS/Normal 五实现）选 worker 并分配 scan range，构建 `ExecutionDAG`。
3. **Deploy**：`Deployer.deployFragments()` 按 `ExecutionSchedule` 策略把 `TExecPlanFragmentParams` 经 **brpc 异步**推给各 BE；FE 只与 root fragment 的 BE 建 `ResultReceiver` 拉结果流。湖仓/自适应场景用 `PhasedExecutionSchedule`（`threeStageExecutionsToDeploy` 三阶段分组，instance 完成回调 `scheduleNextTurn()` 再部署下一批），普通查询 `AllAtOnceExecutionSchedule` 一次性部署。

即"默认直接推送 + 分阶段可选"，**不是两阶段提交**。

### ConnectContext：为什么是 god object（1988 行，被 import 511 次）

它是单连接全生命周期上下文总线：连接层（`mysqlChannel`/`capability`/`connectionId`）、身份（`accessControlContext`/`currentDb`/catalog/warehouse）、执行态（`queryId`/`executionId`/`QueryState`/`executor`/`isKilled`）、会话变量（`sessionVariable` + modified + userVariables）、审计。关键机制是 `ThreadLocal<ConnectContext> threadLocalInfo`（`ConnectContext.java:128`）+ `setThreadLocalInfo()/get()/remove()`——命令在 worker 线程池上跑，鉴权/优化器/调度器多层都要读会话，任何代码可静态取当前会话。这是 511 次 import 的根因：方便，但造成全局隐式耦合。

## 核心实现

### 会话变量（`SessionVariable.java`，6944 行）

字段 + `@VariableMgr.VarAttr(name="...")` 注解（如 `queryTimeoutS` :1388）+ getter/setter，`VariableMgr` 注解扫描自动注册进 SET/SHOW 体系；BE 感知的变量在 `toThrift()`（:6616 起）随计划下发。全局变量走 `GlobalVariable.java` + journal 持久化。

### 超时与故障保护

`StmtExecutor`（:1181）调 `QeProcessorImpl.monitorQuery(executionId, now+timeout)`，`scanMonitorQueries()` 定期扫 `monitorQueryMap` 到期 unregister+cancel；BE 侧 `query_timeout`/`big_query_mem_limit` 由 BE 自杀。`CoordinatorMonitor` 监死 BE 队列 → cancel 所有用到该 BE 的查询；`HostBlacklist`/`SimpleScheduler` 提供重试。

### 响应编码

`QueryState.MysqlStateType`（NOOP/OK/EOF/ERR）状态机 + `setOk/setEof/setError`，`ConnectProcessor.finalizeCommand()` 据此编码 MySQL 响应包。

## 设计模式

| 模式 | 位置 | 为什么用 |
| --- | --- | --- |
| 抽象 + 工厂 | `scheduler/Coordinator.java` + `DefaultCoordinator.Factory`（7 族产品：query/insert/broker load…） | 导入与查询的调度差异大 |
| 策略族 | `BackendSelector`（5 实现）、`ExecutionSchedule`（3 实现）、`SlotProvider` | 选点与分批策略可插拔 |
| ThreadLocal 上下文 + Guard | `ConnectContext.Guard`（:1813，finally 恢复 prev） | session 临时切换的安全恢复 |
| 单例 | `QueryQueueManager`、`CoordinatorMonitor`、`QeProcessorImpl` | 全进程唯一的队列与监控 |

## 模块间交互

- 上游协议字节来自 xnio；`handleQuery` → `parseStatements`（[03 优化器](/vibe-reading/articles/Database/OLAP/StarRocks/CodeWiki/main-2026-08/03-optimizer) 的 SqlParser）→ `StmtExecutor.execute()`（非 leader FE 先 `forwardToLeader()`）。
- 计划生成后调 `rpc/BackendServiceClient` 发 BE；元数据/队列依赖 [01 FE 骨架](/vibe-reading/articles/Database/OLAP/StarRocks/CodeWiki/main-2026-08/01-fe-server) 的 GlobalStateMgr。
- Stream Load 的计划请求（`streamLoadPut`）反向借用本模块的 `LoadPlanner` 与 Coordinator 工厂，见 [08 Load](/vibe-reading/articles/Database/OLAP/StarRocks/CodeWiki/main-2026-08/08-load)。

## 扩展方式

**新增会话变量**：`SessionVariable.java` 加字段 + `@VariableMgr.VarAttr` 注解 + getter/setter；BE 感知则补 `toThrift()` 下发行。

**新增 MySQL command**：`mysql/MysqlCommand.java` 枚举加码 → `ConnectProcessor.dispatch()`（:996 switch）加 case + 新 `handleXxx()`，注意 `handleQuery()` :1119 的 lastQueryId 更新条件需同步。

**改查询超时**：三处联动——`SessionVariable.queryTimeoutS`（默认 300s）、`StmtExecutor` :1181 的 monitorQuery 到期时间、`QueryQueueManager` 排队期顺延逻辑（`LogicalSlot.expiredAllocatedTimeMs`，`QueryQueueManager.java:161`）。

**待核实**：`ResultReceiver` 与 root BE 的 brpc stream 细节；`SlotManager` 在 shared-data 与 shared-nothing 模式下的差异。
