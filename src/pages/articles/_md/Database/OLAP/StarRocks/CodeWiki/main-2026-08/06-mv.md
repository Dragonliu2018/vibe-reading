## 模块定位

StarRocks 的异步物化视图体系是"**MV 即表 + 优化器内改写**"的组合：MV 定义是一张真正的 OlapTable（共享分区/tablet/副本体系），改写则嵌在 Cascades 优化器的 rewrite 阶段（`sql/optimizer/MvRewritePreprocessor`），刷新由 `scheduler/` 的持久化 Task 驱动。它独立成篇因为代码横跨三个包——`catalog/`（模型）、`sql/optimizer/`（改写）、`scheduler/`（刷新），没有单一入口文件能看懂全貌。

## 模块架构

三层协作：数据模型在 `catalog/MaterializedView.java`（3081 行，`extends OlapTable`；Lake 表派生 `lake/LakeMaterializedView`）、改写准备在 `sql/optimizer/MvRewritePreprocessor`（由 `QueryOptimizer.prepareMvRewrite()`（`QueryOptimizer.java:338` 附近）在逻辑改写前调用）、真正改写由 transformation 规则族执行（`rule/transformation/materialization/rule/`）。刷新调度在 `scheduler/TaskManager` + `scheduler/mv/MVRefreshProcessor`（45K 行核心）。

## 调用链路

### 改写主流程（`MvRewritePreprocessor.prepare()`，:133，五步全带 Tracers 计时）

```text

4. getMvWithPlanContext() (:638)   # CachingMvPlanContextBuilder 取 MvPlanContext
   prepareRelatedMVs() (:759)      # MVTimelinessArbiter 计算 MvUpdateInfo（需刷新分区集合），

5. processPlanWithView() (:278)    # view-based rewrite（Lazy OptPlanEvaluator）
```

规则族注册在 `RuleSet.java`（:370/:377）：`SINGLE_TABLE_MV_REWRITE_RULES`（`AggregateScanRule`/`AggregateTimeSeriesRule`/`OnlyScanRule`）与 `MULTI_TABLE_MV_REWRITE_RULES`（`AggregateJoinRule`/`OnlyJoinRule`/`AggregateJoinPushDownRule`）。开关由 `MvRewriteStrategy.prepareRewriteStrategy`（`materialization/MvRewriteStrategy.java:153`，含 DEFAULT/MULTI_STAGES 与 PHASE0-2）仲裁，再经 `RuleSet#addSingleTableMvRewriteRule`（:519）动态注入。规则基类 `BaseMaterializedViewRewriteRule.createRewriter()`（:281）分发到两个 rewriter：`MaterializedViewRewriter`（3077 行，多表 join 结构匹配 + union/view-delta 补偿）与 `AggregatedMaterializedViewRewriter`（聚合补偿，如 SUM 补 COUNT）。

### CachingMvPlanContextBuilder 缓存什么（单例）

- `MV_PLAN_CONTEXT_CACHE`：Caffeine AsyncLoadingCache，key=MaterializedView，value=`List<MvPlanContext>`（一个 MV 多个 plan 是因 view-based rewrite 有 inline/非 inline 两种形态）；未命中不阻塞、只触发异步预热；
- `AST_TO_MV_MAP`：MV 定义 SQL AST 规范化（`AstKey`，去 order-by 变体）→ MV 集合，服务 text-match rewrite；
- `MV_GLOBAL_CONTEXT_CACHE_MAP`：生命周期同 MV 的 per-MV 二级缓存（`MVCacheEntity`）。

控内存时会把 Iceberg/DeltaLake Table 替换成 LightWeight 版（`removeHeavyObjectsFromTable`，:240）。

## 核心实现

### MV 数据模型（`MaterializedView.java` 关键字段）

| 字段 | 语义 |
| --- | --- |
| `MvRefreshScheme refreshScheme`（:523） | `RefreshMoment`（IMMEDIATE/DEFERRED）+ `MaterializedViewRefreshType`（SYNC/ASYNC）+ `AsyncRefreshContext`（:323，定时间隔 + `baseTableVisibleVersionMap` 版本快照——partition 用 name 作 key，因 insert overwrite 会换 partition id） |
| `RefreshMode currentRefreshMode`（:188） | AUTO / **PCT**（partition-change-tracking，默认）/ INCREMENTAL |
| `List<BaseTableInfo> baseTableInfos` | base 表依赖（支持 view 与嵌套 MV） |
| `partitionExprMaps`（:1789/:2500 analyze） | PARTITION BY 其他表列/表达式时的分区推导 |
| `maxMVRewriteStaleness` / `active`/`inactiveReason` | 新鲜度控制与失活原因 |

持久化走一组 journal log（`ChangeMaterializedViewRefreshSchemeLog` 等）。

### 刷新调度

- **定时**：`scheduler/TaskManager` 为每个异步 MV 建持久化 Task（source=`Constants.TaskSource.MV`），`scheduleAtFixedRate` 周期触发 `executeTask()`（含 FE 重启后 lastScheduleTime+period 超时立即补触发）；执行体 `MVTaskRunProcessor.processTaskRun`（:186）→ `MVRefreshProcessor`（分区选择 `MVRefreshPartitionSelector` 按 FORCE/STRICT/ADAPTIVE）。
- **手动**：`REFRESH MATERIALIZED VIEW` → `DDLStmtExecutor`（:424）→ `LocalMetastore.refreshMaterializedView`（:3748，手动优先级更高）。
- **新鲜度事件**：`MVVersionManager` + `MVTimelinessMgr`（`MaterializedViewMgr.triggerTimelessInfoEvent` 接收 `MV_REFRESHED` 等事件），供查询侧 `MVTimelinessArbiter` 判新鲜度；`MVActiveChecker`（LeaderDaemon）周期巡检失活（base 表 schema 变更等），失活 MV 直接被改写淘汰。
- 待核实：数据导入完成直接事件触发 async MV 刷新的路径未找到（PCT 模式下按调度时间点对比版本差决定刷哪些分区）。

## 扩展方式

**新增一种聚合改写规则**：`rule/transformation/materialization/rule/` 新建规则类（继承 `SingleTableRewriteBaseRule` 或 `BaseMaterializedViewRewriteRule`，声明 pattern）→ 注册进 `RuleSet` 的 `SINGLE_TABLE_MV_REWRITE_RULES`/`MULTI_TABLE_MV_REWRITE_RULES`（或新增 `RuleType` 并在 `MvStrategyArbitrator.isEnableMaterializedViewRewrite` 纳入判断）→ 聚合等价性/补偿逻辑在 `AggregatedMaterializedViewRewriter`（roll-up、derived agg 补列）→ 若 MV 定义侧该形态无法生成 SPJG plan，需同步调整 `MvPlanContextBuilder` 的 plan 校验（否则永远进不了候选）→ 加 session 变量开关走 `MvRewritePreprocessor#logMVParams` 清单与 `MvRewriteStrategy`。
