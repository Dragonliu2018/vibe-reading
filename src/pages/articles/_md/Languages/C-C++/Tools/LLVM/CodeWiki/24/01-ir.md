## 模块定位

IR 模块是整条编译流水线的中枢——前端把源码翻成它，中端优化它，后端消费它。它定义了 LLVM 的"通用中间语言"：一套稳定的、与源语言和目标架构都无关的数据模型（`Module`/`Function`/`BasicBlock`/`Instruction`/`Type`/`Value`），以及它的两种序列化格式（`.ll` 文本、`.bc` bitcode）。正因为这套模型独立存在，"多前端共享中后端"才成为可能——换前端只改"源码→IR"的翻译，中后端一行不动。

## 模块架构

IR 模块的核心是一棵**以 `Value` 为根的单根继承树**，辅以读写子系统：

```
                    LLVMContext（全局单例容器，拥有所有 Type/Constant 单例）
                           │
                         Module ──持有──► FunctionList / GlobalList / ValueSymbolTable
                           │
                         Function ──持有──► BasicBlock list / Argument list
                           │
                       BasicBlock ──持有──► Instruction list（ilist）
                           │
    ┌──────────────────────┴──────────────────────────┐
    │  Value（基类：VTy 类型 + UseList 双向链表）       │
    │    ├── User : Value（持操作数 Use[]）              │
    │    │     ├── Constant                            │
    │    │     │     ├── ConstantInt/ConstantFP...     │
    │    │     │     └── GlobalValue → Function/GlobalVariable
    │    │     └── Instruction（ilist_node，知其 BB）   │
    │    ├── BasicBlock : Value                         │
    │    └── Argument : Value                          │
    └──────────────────────────────────────────────────┘

  读写子系统：
    AsmParser  ──LLParser──►  Module          (.ll 文本)
    Bitcode    ──BitcodeReader──► Module       (.bc 二进制，支持延迟物化)
    IRReader   ──parseIR() 统一入口（按 isBitcode() 分流）
```

`Value` 是所有"值"的公共祖先——指令、常量、参数、基本块都是 `Value`。`User` 是"使用其他 Value 作为操作数"的 `Value`，它通过 `Use` 对象与被使用的 `Value` 形成双向边。`Type` 不在 `Value` 树里，而是由 `LLVMContext` 拥有的单例（flyweight）。

## 调用链路

以 `.ll` 文本解析为例，从统一入口 `parseIR` 到构建 `Module` 的调用链：

```
parseIR(MemoryBuffer, Err, Context, Callbacks)               [lib/IRReader/IRReader.cpp:68]
  │  输入：MemoryBuffer → 输出：unique_ptr<Module>
  ├─ isBitcode()? ─yes─► parseBitcodeFile() → BitcodeReader::parseModule()（延迟物化）
  └─ no ─► parseAssembly()
            └─ LLParser::Run()                                 [lib/AsmParser/LLParser.cpp:76]
                ├─ parseTargetDefinitions()                    # target datalayout/triple
                └─ parseTopLevelEntities()                      [LLParser.cpp:563]
                    ├─ kw_declare → parseDeclare()              # 函数声明（无函数体）
                    ├─ kw_define → parseDefine()                # 函数定义
                    │     └─ parseFunctionBody()                [LLParser.cpp:7357]
                    │           └─ parseBasicBlock() → parseInstruction()  # 逐条建 Instruction 插入 BB
                    ├─ GlobalVar → parseGlobal()                # 全局变量
                    └─ validateEndOfModule()                   # 解析前向引用、升级 intrinsic
```

关键方法速查：

| 方法 | 一行职责 | 关键设计决策 |
|------|---------|------------|
| `parseIR` in `IRReader.cpp:68` | 统一读取入口，按格式分流 | 双格式共用入口 |
| `LLParser::Run` in `LLParser.cpp:76` | 递归下降解析文本 IR | 按关键字分发顶层实体 |
| `Value::replaceAllUsesWith` in `Value.h` | 把所有 use 指向新值（RAUW） | 依赖 use-list 双向链表，O(uses) |
| `Type::getInt32Ty` in `Type.h` | 获取 i32 类型单例 | flyweight，指针比较判等 |

## 核心实现

### Value 与 Use 双向链表

`Value` 是 IR 一切对象的基类，核心设计是用 `SubclassID`（非 vtable）做类型标识 + `UseList` 维护"谁用了我"：

```cpp title="include/llvm/IR/Value.h:75"
class Value {
  const unsigned char SubclassID;           // isa/dyn_cast 的类型标识（替代 vtable）
  unsigned NumUserOperands : 28;
  Type *VTy;                                // 此值的类型
  Use *UseList = nullptr;                   // 使用此 Value 的 Use 链表头
public:
  void replaceAllUsesWith(Value *V);        // RAUW — 优化最频繁的操作
  use_iterator use_begin();
};
```

`Use`（`Use.h:35`）是 `Value` 与 `User` 之间的"边"——一个 use 就是"某条指令用了某个值"。它是一个双向链表节点，但 `Prev` 不指向前一个 `Use` 对象，而是指向前一个 `Use` 的 `Next` 字段地址：

```cpp title="include/llvm/IR/Use.h:35"
class Use {
  Value *Val;          // 被引用的 Value
  Use *Next;           // use-list 中的下一个 Use
  Use **Prev;          // 指向前一个 Use 的 Next 字段（或 list head）
  User *Parent;        // 拥有此 Use 的 User
};
```

**为什么这样设计**：编译器优化极频繁地需要 `replaceAllUsesWith`（把一个值替换成另一个）——每次化简都要遍历被替换值的所有 use。双向链表使：从 `Value` 端能遍历 use-list（`use_begin()`），从 `User` 端能遍历 operand-list（`op_begin()`），同一个 `Use` 对象同时存在于两条链中，无冗余存储；`Prev` 指向 `Next` 字段而非对象本身，使链表头插入和单个 `Use` 的删除都是 O(1) 且不需特判头节点。

### Type 单例与 isa/dyn_cast

`Type` 全部由 `LLVMContextImpl` 拥有并 uniqued（`lib/IR/LLVMContextImpl.h:1673`）：

```cpp title="lib/IR/LLVMContextImpl.h:1673"
Type VoidTy, HalfTy, FloatTy, DoubleTy, ...;          // 标准类型直接成员
IntegerType Int1Ty, Int8Ty, Int16Ty, Int32Ty, ...;
DenseMap<unsigned, IntegerType*> IntegerTypes;        // 非标准宽度整数 uniquing
DenseMap<std::pair<Type*,uint64_t>, ArrayType*> ArrayTypes;
DenseMap<unsigned, PointerType*> PointerTypes;        // 指针按 address space uniqued
```

`Type::getInt32Ty(C)` 等工厂方法返回已 uniqued 的单例。类型注释明确（`Type.h:38`）：*"only one instance of a particular type is ever created. Thus seeing if two types are equal is a matter of doing a trivial pointer comparison."*

**为什么不用 vtable**：`Value` 的析构函数注释（`Value.h:217`）写道："Value's destructor should be virtual by design, but that would require that Value and all of its subclasses have a vtable that effectively duplicates the information in the value ID. As a size optimization, the destructor has been protected." 一个大程序可能产生数百万个 `Value`，每个 vtable 指针占 8 字节就是 GB 级冗余。`SubclassID` + `isa<Instruction>(V)`/`dyn_cast<AllocaInst>(I)` 模板（`Support/Casting.h`）在零虚函数开销下实现类型安全 downcast。

### Module 所有权与 ilist

`Module`（`Module.h:67`）是顶层容器，集中持有所有全局对象：`GlobalList`、`FunctionList`、`AliasList`、`IFuncList`、`NamedMDList`、`ValueSymbolTable`、`DataLayout`、`Triple`。`Function`/`BasicBlock`/`Instruction` 的列表都用侵入式链表 `ilist`（`ADT/ilist.h`）——节点自身继承 `ilist_node_with_parent`，不需要外部容器分配节点，插入/删除 O(1)，且节点知道自己的 parent（`Instruction` 知道在哪个 `BasicBlock`，`BasicBlock` 知道在哪个 `Function`）。

**为什么集中所有权**：IR 是一个完整编译单元，所有全局对象生命周期应与编译单元一致。`Module` 析构级联释放 `Function`→`BasicBlock`→`Instruction`，避免泄漏；`ValueSymbolTable` 统一管理命名查找支持跨函数引用解析。

### Opaque Pointers

LLVM 15+ 统一指针为 `ptr`（opaque pointer），`PointerType` 仅按 address space 区分（`LLVMContextImpl.h:1702`），不存储 pointee type。**为什么**：typed pointer（`i32*`、`i8**`）在实际编译器中几乎不提供有用类型安全（bitcast 太容易绕过），却造成 IR 膨胀和前端不自然的类型转换；opaque pointer 让 IR 更简洁，类型安全由前端保证，后端只关心数据布局与操作语义。

## 设计模式

| 模式 | 位置 | 为什么用 |
|------|------|---------|
| Visitor（InstVisitor） | `llvm/IR/InstVisitor.h:78` | pass 按指令类型分发，CRTP 生成 switch 替代虚函数，注释明确"avoid virtual function call overhead" |
| Builder（IRBuilder） | `llvm/IR/IRBuilder.h:2893` | 封装指令创建（插入位置/常量折叠/debug loc），`B.CreateAdd()` 等 |
| Flyweight/Singleton | Type/Constant in `LLVMContextImpl.h:1673` | 类型相等性退化为指针比较 O(1) |
| 自描述类型标识 | `Value.h:76` SubclassID + `Casting.h` isa/dyn_cast | 替代 vtable RTTI，省百万对象级内存 |
| Intrusive List（ilist） | `ADT/ilist.h` + `SymbolTableListTraits.h` | 零分配、自动维护符号表、节点知 parent |

## 模块间交互

IR 模块是最高扇入的中枢——几乎所有 pass（`lib/Transforms`、`lib/CodeGen`、`lib/Analysis`）、前端 Clang、LTO、LLD 都直接操作它的数据模型。它向下只依赖 `llvm/ADT`（`APInt`/`DenseMap`/`ilist`/`StringRef`）和 `llvm/Support`（`Casting`/`MemoryBuffer`/`SourceMgr`）。`LLVMContext` 是全局唯一状态容器，所有 `Type`/`Constant` 单例依附于它；`Module` 是所有权根，析构级联释放。交互方式是头文件直暴露数据模型类，其他模块直接 `#include` 并操作指针。

## 扩展方式
